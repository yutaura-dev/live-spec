# live-spec の spec を書く

live-spec は「AI が書き、人が図と画面で読む」仕様書のツール。spec は素の TypeScript で書き、live-spec がそれを**実行**して、状態遷移図・できる／できない理由・画面・検査結果を生成する。人は spec のコードではなく生成物を読むので、spec は「実行すると正しい図と理由が出る」ように書く。

## spec が先、実装が後

振る舞い（誰が・いつ・何をできるか、画面に何が出るか）の正本は spec で、実装は spec に従う。

1. 振る舞いを変えるときは、実装より先に spec を直す
2. `live-spec diff` と生成した仕様書を人に見せ（live-spec-review）、振る舞いが決まってから実装する
3. 実装が spec のとおりかは、実装のテストで確かめる。テストの名前に `specOf` を使って spec の項目と結ぶ（下の「実装のテストと結ぶ」）
4. 実装に合わせて spec を書き換えない。実装の途中で spec の誤りや抜けに気づいたら、実装を止めて spec の変更として人に見せる。決められなければ未決事項にする

spec からコードの場所を指さない（ファイル名や行番号をコメントに残さない）。spec がコードを指すと、「コードが変わったら spec を合わせる」逆向きの流れになるため。spec と実装の対応は、テストの側から spec を指して持つ。

## 実行のしかた

live-spec は npm パッケージ `@yutaura/live-spec`（`npm i -D @yutaura/live-spec` / `pnpm add -D @yutaura/live-spec`）で、`live-spec` コマンドを持つ。

| やりたいこと | コマンド |
|---|---|
| Markdown を見る | `npx live-spec specs/`（spec が 1 つなら標準出力、複数なら `--out <ディレクトリ>`） |
| HTML を書き出す | `npx live-spec specs/ --html --out spec.html` |
| ブラウザで見ながら書く | `npx live-spec specs/ --serve` |
| 変更前と比べる | `npx live-spec diff specs/ [--base <リビジョン>] [--head <リビジョン>] [--html --out <ファイル>]` |
| 型チェックと検査（CI 向け） | `npx live-spec check specs/`（型の誤り・検査結果・未確認の確かめてほしい点があれば終了コード 1） |

（live-spec リポジトリ自身の中では `pnpm spec ...`）

**1 つの spec ファイルが 1 つのドメインオブジェクト**になる。プロジェクトの仕様は `specs/` のようなディレクトリに spec を並べ、ディレクトリごと渡す。

- HTML: `live-spec specs/ --html --out spec.html`。ドメインオブジェクトごとのページとタブを持つ 1 つのファイルになる（`#/<名前>` でページを開ける）
- Markdown: `live-spec specs/ --out docs/spec/`。ドメインオブジェクトごとの `<名前>.md` と一覧の `README.md` を書き出す

spec では `import { ensure, ui, api, cli } from "@yutaura/live-spec"` と書いて読み込む（live-spec リポジトリ自身の `specs/` と `examples/` だけは `../src/index.ts` から読み込む）。

仕様書の生成（`live-spec specs/`）は型を消して実行するだけなので、型の誤りでは止まらない。書き終えたら `npx live-spec check specs/` で型チェックと検査をまとめて行う。型チェックには、実行したディレクトリから見える typescript を使う（monorepo で typescript が別のパッケージにあるなら `--cwd <そのパッケージ>`）。

## spec の形

| export | 必須 | 役割 |
|---|---|---|
| `initial` | ✓ | 初期状態（オブジェクト）。誰が・どんな入力で作れるかに決まりがあるなら、作る操作の関数 `(登場人物, ...入力) => 状態`（下の「作る操作」） |
| `actors` | ✓ | 探索に使う登場人物の具体例（`{ 名前: 値 }`） |
| 上記と下記以外の関数 | | 操作。`(状態, 登場人物, ...入力) => 次の状態` |
| `invariants` | | 不変条件。`{ 説明: (状態) => boolean }`。引数を 2 つとる `(遷移の前, 遷移の後) => boolean` は遷移の不変条件 |
| `inputs` | | 3 つ目以降の引数の例。`{ 操作名: { 例の名前: [引数...] } }`。作る操作の入力は `initial` に書く（登場人物のあとの引数） |
| `surface` | | `(状態, 登場人物) => 画面 \| null` |
| `scenarios` | | `{ 名前: [{ do: 操作, by: "登場人物", input?: "例の名前", expect?: { 項目: 値 }, denied?: "理由" }] }`。`denied` は「この手順は断られるはず」 |
| `questions` | | `[{ ask, about?: 操作 \| { 項目: 値 }, scenario?: "シナリオの名前", note? }]` |
| `links` | | `[{ from?: 操作, to: "相手の名前", action?: "相手の操作名", label }]` |
| `decisions` | | `{ 名前: { decide: (入力) => 結果, cases: [{ input, expect? }] } }` |
| `glossary` | | `{ 用語: "説明" }` |
| `diagram` | | `{ groupBy: "status" }`。HTML の要約の図で状態をまとめる項目。書かなければ最初の文字列の項目。状態を項目の組で表して図が込み入るときは、モデルから項目を外さずに、ここで見せ方をまとめる |

状態の型の JSDoc は仕様書の冒頭の説明に、関数の JSDoc の最初の段落（空行まで）は操作の見出しになる。読み手が業務の言葉で理解できる文を書く。見出しは短く、詳しい説明は空行のあとの段落に書く（仕様書には出ないが、spec を読む人の役に立つ）。

## モデルの作り方

spec は DDD（ドメイン駆動設計）の集約を 1 つ書いたものに当たる。何を 1 つの spec にするか、状態に何を入れるか、不変条件をどこに書くかで迷ったら、[live-spec-domain-modeling](../live-spec-domain-modeling/SKILL.md) を読む。

### 0. ドメインオブジェクトに分ける（最初に決める）

1 つの spec には 1 つのドメインオブジェクト（記事、注文、ジョブ、サーバ、ブラウザのタブ…）だけを書く。**状態は 10 個前後に収まるのが目安**。それを超えるなら、関心の違うものを 1 つに詰め込んでいないかを疑う。

- 独立した項目（例: サーバの状態 × ブラウザのタブの状態 × 生成の結果）を 1 つの状態にまとめると、状態が組み合わせの数だけ増え、名前も `none · placeholder · listening · stale` のような読めないものになる。項目ごとに、それを持つドメインオブジェクトへ分ける
- 分けたオブジェクトどうしの関係（「サーバが止まるとタブは古いまま残る」など）は、それぞれの spec の操作・条件・JSDoc に書く。1 つの状態機械にまとめ直さない
- 状態の名前（ラベル）は、文字列の項目の値がそのまま使われる。`status: "受付待ち"` のように、読み手の言葉で値を付ける
- 名前に並ぶ項目は、`initial` に書いた順になる。読み手に最初に見せたい項目（ふつうは `status`）を先に書く

### 1. 型には全部の項目を書き、振る舞いを変える値は有限にする

状態の型には、そのドメインオブジェクトが持つ項目を全部書いてよい（題名・本文・ID・手順の並びなど）。仕様書のプロパティの表に、型と JSDoc が出る。取りうる値を列挙していない型（`string`、`number`、配列、オブジェクト）で、操作・不変条件・目指す状態の関数のどこからも読まない項目は「データ」として扱われ、状態の見分けと名前に使われない（値が違っても状態は増えない）。画面（`surface`）で表示に使うだけなら、データのまま。

値の一覧は、文字列の union か `as const` のオブジェクト（`const Status = { todo: "todo", … } as const; type Status = (typeof Status)[keyof typeof Status]`）で書く。オブジェクトの各値に付けた JSDoc は、プロパティの表で値ごとの説明として出る。

種類・担当のように「作ったときに決まって変わらないが、振る舞いは変える」値（値の一覧を持ち、条件で読むが、どの操作も書き換えない項目）は「作ったときに決まる値」として扱われ、項目ごとに 1 つずつ値を変えた初期状態からも探索される。`initial` には代表の値を 1 つ書けばよい。組み合わせで振る舞いが変わるもの（種類が「待つ」で担当が Claude のときだけ、など）は、`export const variants = [{ kind: "wait", assignee: "claude" }]` に書き足す（全部の組み合わせは状態の数の上限を超えやすいので、既定では試さない）。

以下は、振る舞いを変える値（条件で読む項目）についての決まり。

live-spec は初期状態から操作を全部実行して、到達できる状態をすべて列挙する。題名・本文・金額のような値を状態に入れると、値の数だけ状態が増えて図が読めなくなる（上限 500 で打ち切られる）。

- 入れる: `status`、`pinned` のように「できる／できない」を左右する値、所有者の ID（「自分の記事だけ」のため）
- 入れない: 表示用の文字列、日時、件数。条件に効くなら `hasComment: boolean` のように有限の値に抽象化する
- 有限の値は文字列リテラルの union か `boolean` で型を書く。型と同じファイルに置くと「型にあるのに到達しない値」を検出できる

### 2. 登場人物は「条件を区別できる最小の組」にする

ロールだけでなく、条件を分ける具体例を並べる。所有者の条件があるなら「所有者」と「同じロールの別人」の両方を入れないと、「自分の〜だけ」という理由が表に出てこない。ワーカーやバッチのようなシステムも登場人物にする（クライアントが起こせない遷移を表せる）。

```ts
export const actors = {
  著者alice: { id: "alice", role: "author" },   // 所有者
  別の著者bob: { id: "bob", role: "author" },   // 同じロールの別人
  編集者eve: { id: "eve", role: "editor" },
  ワーカー: { kind: "worker" },
};
```

### 3. 操作は ensure を「誰が → いつ → 何を入力したら」の順に並べる

できない理由として表に出るのは**最初に失敗した ensure** だけ。live-spec は実行結果から「誰が」「いつ」「入力」の軸に振り分けるが、順序をそろえておくと理由が読みやすくなる。

- 理由は読み手向けの短い文にする（「編集者だけ」「レビュー中のときだけ」「差し戻し理由が必要」）。同じ条件には同じ文言を使う（表でまとめられる）
- 新しいオブジェクトを返す。引数を書き換えない
- 「できない」は ensure で表す。普通の `throw` や、想定外の値による `TypeError` は**仕様のバグ**として検出される

### 4. 不変条件は「1 つの状態について常に成り立つこと」

`invariants` の説明文は、破ったときにそのまま表示される。破る状態は、初期状態からの最短手順と一緒に報告される。

遷移の前後を比べる性質（ライフサイクルの決まり）は、引数を 2 つとる関数で書く。探索で見つけたすべての遷移について、遷移の前と後の状態で確かめ、破った遷移を最短手順と一緒に報告する。

```ts
const isFinished = (job: Job) => job.status === "succeeded" || job.status === "cancelled";

export const invariants = {
  成功か取り消しで終わったジョブは変わらない: (before: Job, after: Job) => !isFinished(before) || before.status === after.status,
};
```

状態についての `ensure`（「待機中のときだけ」など）の多くは、ライフサイクルの決まりを 1 つ書くと、その決まりで確かめられるようになる（「意図がほかに書かれていない条件」が消える）。遷移の不変条件は操作の名前や登場人物を受け取らないので、「誰が」についての決まりは `denied` のシナリオで書く。

### 4.5 誰が・どんな入力で作れるかは、作る操作で書く

「著者だけが記事を書き始められる」「題名がないと作れない」のように、作ることにも決まりがあるなら、`initial` をオブジェクトではなく関数で書く。登場人物と `inputs.initial` の入力の例のすべての組で実行し、作れた結果をそれぞれ初期状態にする。止まった組は、仕様書の操作の最初に「作れない理由」として出る。

```ts
export const inputs = { initial: { ニュース: ["news", "速報"], 題名が空: ["news", ""] } };

/** 記事を書き始める */
export function initial(user: User, kind: Article["kind"], title: string): Article {
  ensure(user.role === "author", "著者だけ");
  ensure(title.trim() !== "", "題名が必要");
  return { status: "draft", kind, featured: false, authorId: user.id };
}
```

- 戻り値の型（`: Article`）を書く。状態の型をそこから読む
- 作ったときに決まる値（種類など）は入力の例で値ごとに作る。作る操作があるときは `variants` と、値ごとの初期状態の自動探索は使わない
- シナリオは最初の手順に `{ do: initial, by: "著者alice", input: "ニュース" }` を書いて始める。`denied` を付ければ「作れないはず」も書ける。`given` は使えない
- 作る人を所有者にする（`authorId: user.id`）と、作れる登場人物の数だけ同じ形の初期状態が並ぶ。所有者の条件を確かめたいなら、作れる登場人物を 1 人にする
- 誰がいつ作ってもよいなら、`initial` はオブジェクトのままでよい

### 5. 入力の例には「通る例」と「止まる例」を両方入れる

`inputs` は名前付きの具体例。止まる例がないと「できない入力」の欄が出ない。3 つ以上の引数をとる操作に例がないと、その操作は実行されない（`missing-inputs` として報告される）。

### 6. 画面（surface）は見る人ごとに返す

- UI: `ui.screen(title, ...)`。子には `ui.section / heading / text / field / button / badge / list`。`cond && ui.button(...)` のように出し分けてよい
- ボタンには操作の**関数そのもの**を渡す（`ui.button("公開する", publish)`）。文字列にしない
- API: `api.request(method, path, body?)` / `api.response(status, body?)`。CLI: `cli.output(text)`
- 見える画面がない人（API を呼ばないワーカーなど）には `null` を返す
- UI の画面では、ボタンと実行できる操作が食い違うと検出される。見せるだけのボタンは `{ disabled: true }`
- **ボタンで起きない操作は `ui.screen` で描かない**。ブラウザでページを開く・再読み込みする、ファイルを保存する、外部のイベントが届く、といった操作は画面のボタンでは起きない。`ui.screen` で描くと「実行できるのにボタンがない」が大量に出て、それを消すために架空のボタンを足すと仕様が不正確になる。その人に見えるものを `cli.output` や `api.response` で返すか、見えるものがなければ `null` を返す

### 6.5 用語と項目の説明を書く

状態の名前（`inReview`）や項目（`pinned`）だけでは意味が伝わらないことがある。状態の型の各項目に JSDoc（`/** 公開の段階 */ status: ...`）を付け、値や業務の言葉は `export const glossary = { inReview: "編集者のレビュー待ち" }` に書く。仕様書の「用語」の節に並び、状態遷移図のノードにカーソルを合わせると説明が出る。

### 6.6 条件の組み合わせが多いルールは判断表にする

送料・割引・料金区分のように「入力の組み合わせ → 結果」で決まるルールは、状態遷移ではなく `decisions` に書く。判断の関数（`decide`）と入力の例（`cases`）を書くと、live-spec が実行して表にする。境界の値（4999 円と 5000 円など）を例に入れ、`expect` を付けておくと、期待と違うときに検査結果に出る。

### 6.7 上限つきの回数は、振る舞いに効く区分だけを持つ

再試行の上限（既定 3 回）のような回数を `attempt: 0 | 1 | 2 | 3` のまま状態に入れると、ほかの項目と掛け合わさって状態が増え、図が読めなくなる。振る舞いに効くのが「まだ残っている／いまが最後／使い切った」だけなら、その区分だけを状態に持ち、「次が最後になるか」は入力で与える。

```ts
export type Run = {
  status: "queued" | "running" | "failure";
  /** 試行の残り。回数そのものではなく、振る舞いに効く区分だけを持つ */
  retries: "残りあり" | "最後" | "使い切った";
};

export const inputs = { reserve: { まだ残る: [false], 次が最後: [true] } };

/** 試行を 1 回分予約する */
export function reserve(run: Run, worker: Worker, nextIsLast: boolean): Run {
  ensure(run.retries !== "使い切った", "試行が残っているときだけ");
  return { ...run, retries: run.retries === "最後" ? "使い切った" : nextIsLast ? "最後" : "残りあり" };
}
```

この形では「まだ残る」を何度でも選べるので、spec は実際より多くの道筋を探索する（4 回目も「まだ残る」を選べる）。実際にありうる道筋は取りこぼさない、安全側の近似なので、袋小路や不変条件の違反を見落とすことはない。ただ、実際には起きない道筋も図に出る。上限に届くまでの流れを見せたいときは、シナリオに入力を明示して書く（「まだ残る」→「次が最後」→ 失敗）。

回数そのものが振る舞いを変える（3 回目だけ人に知らせる、など）なら、回数を状態に入れる。そのときは、ほかの関心を別のドメインオブジェクトに分けて、状態の掛け合わせを減らす。

### 7. シナリオで業務の流れを書く

状態の一覧だけでは業務の流れが読めない。代表的な流れ（正常系 1〜2 本と、差し戻し・やり直しのような分岐 1〜2 本）を `scenarios` に書く。各手順には操作の**関数**を渡し、要所に `expect` を書く。シナリオは初期状態から実行され、止まったり期待と違ったりすると検査結果に出るので、受け入れテストを兼ねる。シナリオ名は業務の言葉で（「書いて公開するまで」）。

「できない」ことも、大事なものはシナリオに書く。手順に `denied: "理由"` を付けると「この手順は、この理由で断られるはず」という意味になり、実行できてしまうとシナリオが失敗する（`{ do: reject, by: "編集者eve", input: "理由が空", denied: "差し戻し理由が必要" }`）。入力の検証（「--html と --json は同時に指定できない」）や「誰が」の条件は、状態についての条件ではないので不変条件では書けない。こうした条件の意図は `denied` で書く。

作ったときに決まる値（種類・担当など）ごとの流れは、シナリオを `{ given: { kind: "wait" }, steps: [...] }` と書いて、その値の初期状態から始める。`given` に書けるのは作ったときに決まる値だけで、探索していない組み合わせ（2 つ以上の項目を変えたもの）は `variants` に足す。

### 8. 判断できないことは未決事項にする

要件やコードから決められないこと（「アーカイブした記事を戻せるか？」）は、推測で spec に書かずに `questions` に書く。対象の操作（関数）か状態（`{ status: "archived" }`）を `about` に付けると、仕様書の図とカードに印が出る。人は未決事項だけを見れば判断すべき点が分かる。今の動きを写しただけで、正しいと決めていないシナリオ（既存のコードから書き起こしたものなど）は、`scenario: "シナリオの名前"` で未決事項に結ぶ。結ばないと ✅ が付き、合意済みの仕様に見える。

### 8.5 値オブジェクトは別のファイルに書く

作業する場所・金額・期間のように、識別子もライフサイクルも持たない値（DDD の値オブジェクト）で、複数の spec が使うものや、値そのものに決まり（「URL は http か https で始まる」）があるものは、`<名前>.value.ts` に書く。型・`invariants`（`{ 説明: (値) => boolean }`）・`examples`（`{ valid: { 名前: 値 }, invalid: { 名前: 値 } }`）を export する。正しい例が決まりを満たし、正しくない例が決まりを破ることを `live-spec check` が確かめる。spec からは `import type` で型を使う。値オブジェクトは状態遷移を持たないので、操作や `initial` は書かない。

### 8.6 集約の中に Entity が複数あるときは、集約のファイルでまとめる

Task とその中の Action Item のように、ルートを通してしか操作されないが自分のライフサイクルを持つ Entity があるなら、1 つの spec に詰め込まない（状態が掛け合わさって図が読めなくなる）。Entity ごとに spec を書き、`<名前>.aggregate.ts` に `root`・`entities`（spec の名前の文字列）・集約の JSDoc・`displayName` を書く。集約をまたぐ決まりは `invariants` に `(ルートの状態, 中の Entity の状態の配列) => boolean` で書く（今は表示だけで、まだ確かめない）。中の Entity の `links` は、ルートの操作へ向けて書く。集約の外の spec からは、中の Entity ではなくルートを指す。

### 9. ほかのドメインオブジェクトとのつながりを書く

データとして相手を持つ関係（記事の著者、利用者の記事一覧）は、状態の型の項目の型で書く（`author: User`、`posts: Post[]`。`User` は相手の spec の状態の型）。一覧ページに「関連」の図が出る。ID だけを持つ項目は `/** @ref user */ authorId: string` と相手の spec の名前を書く。関連の項目は「どの可否にも影響しない項目」の候補に出ない。


ある操作がほかのオブジェクトの操作を引き起こすなら（「注文したら支払いを確定する」）、送り出す側の spec に `links` を書く。相手は名前の**文字列**で書く（関数を import しない。--watch で読み直すときに別の実体になり、照合できないため）。名前の誤りはプロジェクト全体を生成したときに検出される。

## 手順

1. ドメインオブジェクトを洗い出し、1 オブジェクト 1 ファイルで `specs/` などに置く
2. 状態の型・初期状態・登場人物を書く
3. 操作を書く。JSDoc の 1 行目は業務の言葉で
4. 生成して読む: `pnpm spec <ファイル>`（Markdown が標準出力に出る）
5. 「検査結果」を 1 件ずつ判断する（下の表）。モデルの誤りなら直し、仕様として正しい／判断できないものは報告に残す
6. 型チェックを通す
7. 人に見せる: `live-spec specs/ --serve`（ブラウザで自動更新）か `--html --out <ファイル>`。生成した HTML は**自分でも開いて見る**（状態遷移図が読めるか、操作カードが状態名の壁になっていないか）。検査が通っても、人が読めなければ仕様書としては失敗
8. 人が承認したら実装する。条件ごとに実装のテストを書き、`specOf` で spec の項目と結ぶ

## 検査結果の読み方

| 検査結果 | 意味 | よくある直し方 |
|---|---|---|
| 不変条件を破る | ある操作の結果が条件に反する（遷移の不変条件なら、ある遷移の前後が決まりに反する） | 操作の戻り値か ensure を直す。仕様として正しいなら不変条件を見直す |
| 作る操作が例外を投げた | initial の中で ensure 以外の例外（仕様のバグ） | 入力の例と、作る操作の中の参照を直す |
| 誰も実行できない操作 | どの状態・登場人物でも ensure を通らない | 到達できる状態に条件を合わせる／必要な登場人物を足す |
| 型にあるのに到達しない値 | union の値に遷移する操作がない | 操作を足す。不要な値なら型から消す |
| 例外を投げた | ensure 以外の例外（仕様のバグ） | 想定外の状態での参照を直す。止めたいなら ensure にする |
| オブジェクトを返さなかった | 操作の戻り値が不正 | 新しい状態オブジェクトを返す |
| inputs に例がない／存在しない操作 | 引数の例の不足・名前の誤り | `inputs` を直す |
| ボタンが見えるが実行できない／実行できるがボタンがない | 画面と操作の食い違い | 表示条件を ensure にそろえる。意図的なら `disabled` |
| 状態数の上限で打ち切り | 値が増え続ける項目がある | その項目を状態から外すか、有限の値に抽象化する |

## 「確かめてほしい点」の直し方

live-spec は spec を実行した結果から、条件の書き忘れ・書き間違いの候補を、仕様書の上部の「確かめてほしい点」に ID つきで出す。AI が書いた spec の漏れを見つける主な手がかりなので、1 件ずつ次の順で判断する。

| 候補 | 疑うこと |
|---|---|
| 誰でもできる（`anyone-can`） | 「〜だけ」の書き忘れ |
| いつでもできる（`anytime`） | 状態の条件の書き忘れ |
| 入力を見ていない（`ignores-input`） | 入力の検証の書き忘れ |
| 本人と別人を区別しない（`same-for-similar-actors`） | 「自分の〜だけ」の書き忘れ |
| 結果がまったく同じ入力の例・登場人物（`indistinguishable-*`） | 例や人を分けるはずの条件の書き忘れ。または、違いを状態として表していない |
| 目指す状態にたどり着けない（`cannot-reach-goal`） | 終端ではないのに抜け出せない袋小路。`export const goals = { 成功: (s) => s.status === "success" }` を書いたときだけ出る。書き起こしの spec では、実装で見落とされている袋小路であることが多い |
| 振る舞いが同じ状態（`equivalent-states`） | どの操作・登場人物・入力でも、できる／できないと行き先（と画面）が同じ状態。1 つの状態にまとめる（状態には振る舞いを変える値だけを入れる）か、違いを生む条件の書き忘れ |
| どの可否にも影響しない項目（`unused-field`） | その項目を使う条件の書き忘れ。または、振る舞いに関係しない値を状態に入れている |
| 意図がほかに書かれていない条件（`unguarded`） | 外すと振る舞いが変わるのに、不変条件・シナリオ・画面のボタンのどれも気づかない条件 |

1. **要件・コードと照らして、本当に漏れか**を確かめる。漏れなら spec を直す
2. 意図どおりなら、**その意図をもう 1 か所に書けないか**を考える。状態についての性質なら不変条件、入力や「誰が」についてなら `denied` の手順を持つシナリオ（`unguarded` はこれで消える）
3. それでも意図どおりで、書き足す意味のある性質がないなら、`export const reviewed = { "ID": "理由" }` に理由を書く。仕様書では「確認済み」として理由つきで残る
4. 判断できないなら、未決事項（`questions`）にする。`about` でその候補の状態か操作を指すと、候補は「判断待ち（未決事項）」に移り、`live-spec check` も失敗に数えなくなる。未決事項を消す（判断する）と、また候補として出る

候補を消すためだけに、中身のない不変条件やシナリオを書かない。`reviewed` の理由も「意図どおり」だけで済ませず、なぜそれでよいかを要件の言葉で書く（「カードはどの列からでも動かせる。アーカイブも API では動かせる（未決事項 6）」）。`reviewed` の ID が候補のどれにも当たらなくなると検査結果に出るので、そのときは消す。

## 条件の理由と「通るのは」を突き合わせる

操作の節の「条件」には、`ensure` ごとに「理由の文 — 通るのは〜のとき」が並ぶ。「通るのは」は、その `ensure` だけを効かせて実行して求めた事実。理由の文と食い違っていれば、条件か理由のどちらかが間違っている（「実行中のときだけ」— 通るのは status が queued のとき）。書き終えたら全部の条件について読み比べる。状態の取り違えのような書き間違いは、ほかの検査ではほとんど見つからない。

「この条件がなくても振る舞いは変わらない（ほかの条件と重なっている）」と出る条件は、できない理由の文言を分けたくて重ねているなら残してよい。そうでなければ消す。「（後の条件のために型を絞る条件）」と出るもの（判別 union の `actor.kind === "human"` のあとで `actor.via` を読む、など）は、消すと型が通らないので残す。

## 実装のテストと結ぶ

```ts
import { describe, it } from "vitest";
import { specOf } from "@yutaura/live-spec/testing";
import * as Todo from "../specs/todo.spec.ts";

describe(specOf(Todo.complete), () => {
  it(specOf(Todo.complete, "作った人だけ"), async () => {
    // 別の人が完了にしようとすると断られることを、実装で確かめる
  });
});
it(specOf(Todo, { scenario: "作って完了して取り消す" }), async () => { /* … */ });
```

- `specOf` はテストの名前の文字列を返すだけなので、vitest・`@effect/vitest`・jest・playwright のどれでも使える。操作は関数そのものを渡し（名前を変えると型チェックで落ちる）、条件は `ensure` の理由の文で指す。spec にない条件を渡すと、テストを定義した時点で失敗する
- `live-spec check specs/ --tests <テストのディレクトリ>` がテストのファイルを読み（実行はしない）、spec の項目と結ぶ。どのテストも指していない条件は「確かめてほしい点」に `untested:操作:理由` として出る。spec にない項目を指すテスト（spec を先に変えたあとの古いテスト）は検査結果に出る
- 仕様書も `--tests` を付けて作ると、条件ごとに確かめているテストの場所が出る
- テストで確かめられない条件（画面でしか止めていない、など）は、理由を書いて `reviewed` に入れる

## 人への渡し方

生成物（HTML）と一緒に、次を短く伝える。人は spec のコードを読まない前提で書く。

- 何をモデルにしたか（対象、状態、登場人物）
- どこを抽象化したか（状態から外した値と理由）
- 検査結果のうち、あえて残したものと理由
- 判断が必要な点（質問の形で）
