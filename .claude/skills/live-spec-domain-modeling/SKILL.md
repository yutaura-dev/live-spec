# DDD の知識で spec のモデルを決める

live-spec の spec は、DDD の**集約**を 1 つ書いたものになっている。操作は集約へのコマンド、`ensure` はその事前条件、`invariants` は集約の不変条件に当たる。そのため、DDD で集約を設計するときの考え方が、そのまま spec のモデルの決め方に使える。

この skill は「何をどうモデルにするか」を扱う。export の形・CLI の使い方・検査結果の直し方は [live-spec-authoring](../live-spec-authoring/SKILL.md) に従う。

## 対応表

| live-spec | DDD | 一言で |
|---|---|---|
| spec ファイル 1 つ（ドメインオブジェクト） | 集約 | 一緒に守る必要がある不変条件の範囲 |
| 状態の型 | 集約ルートのエンティティ | ライフサイクル（`status` など）を持つもの |
| 状態の中のオブジェクト・判別 union | 値オブジェクト | 識別子を持たず、値が同じなら同じもの |
| `/** @ref user */ authorId` | ほかの集約への参照 | オブジェクトを埋め込まず、ID で指す |
| `export function initial(登場人物, ...入力)` | ファクトリ | 誰が・どんな入力で作れるか |
| 操作（export した関数） | コマンド | 業務の動詞。`(状態, 登場人物, ...入力) => 次の状態` |
| `ensure(条件, "理由")` | 事前条件 | 理由の文はユビキタス言語で書く |
| `invariants` の `(state) => boolean` | 集約の不変条件 | どの状態でも成り立つこと |
| `invariants` の `(before, after) => boolean` | 遷移の不変条件（ライフサイクルの決まり） | どの遷移でも成り立つこと |
| `links` | 集約をまたぐ反応（ポリシー） | 「〜したら、相手の〜を起こす」。相手とは結果整合性で足りる |
| `decisions` | ポリシー・仕様パターン | 状態に依らない業務ルールの判断表 |
| `glossary`・JSDoc・`ensure` の理由・操作の見出し | ユビキタス言語 | 業務の人が使う言葉 |
| `specs/` ディレクトリ | 境界づけられたコンテキスト | 同じ言葉が同じ意味で通じる範囲 |
| `questions` | 知識の噛み砕き | 推測で埋めずに業務の人に聞く |
| `surface` | アプリケーション層・UI | ドメインの外。見え方だけを書く |

## 手順

### 1. 集約の境界を、不変条件で決める

最初に「いつも成り立たなければならないこと」を業務の言葉で書き出す。**同時に成り立たせる必要がある条件の範囲が 1 つの集約（1 つの spec）**になる。

- 「固定できるのは公開中の記事だけ」→ 固定（`pinned`）と公開の段階（`status`）は同じ集約に入れる
- 「注文の合計が上限を超えない」→ 明細と注文は同じ集約。在庫は、注文の確定と同時に減っていなくてもよいなら別の集約にする

集約は小さく保つ。状態が 10 個を超えたり、状態の名前が `none · placeholder · listening · stale` のような値の羅列になったりしたら、同時に守る必要のない関心が混ざっている。分けた集約どうしは、手順 6 のつながりで書く。

### 2. 状態の項目を 4 つに分ける

状態の型の項目を、DDD の見方で次の 4 つに分ける。分けた結果が、live-spec の扱い（条件で読む・作ったときに決まる・データ）にそのまま対応する。

| 種類 | 例 | 書き方 |
|---|---|---|
| ライフサイクル | `status`, `pinned` | 文字列リテラルの union か `boolean`。操作が書き換える |
| 作ったときに決まる値 | 種類、担当、プラン | 値の一覧を持つが、どの操作も書き換えない。作る操作の入力で決める |
| ほかの集約への参照 | 著者、所属するプロジェクト | ID の項目に `/** @ref user */`。「自分の〜だけ」に使うなら条件で読む |
| データ（値オブジェクトを含む） | 題名、本文、住所、金額 | 振る舞いを変えないなら、条件で読まない。値が違っても状態は増えない |

- ほかの集約を**オブジェクトのまま埋め込まない**。埋め込むと、相手の状態まで探索の対象になり、状態が掛け算で増える。ID で参照し、相手の振る舞いは相手の spec に書く
- ルートを通してしか操作されないが、自分のライフサイクル（状態遷移）を持つ Entity（Task の中の Action Item など）は、集約の中の Entity として別の spec に書き、`<名前>.aggregate.ts` でルートとまとめる。外から ID で直接操作されるか、ルートへの反映があとからでよいなら、別の集約にする
- 複数の spec が使う値オブジェクトや、値そのものに決まりがある値オブジェクトは、`<名前>.value.ts` に型・正しい値の決まり（`invariants`）・正しい例と正しくない例（`examples`）を書き、spec からは型を import する。値オブジェクトは状態遷移を持たないので、専用のページは作られず、一覧ページの節に出る
- 値オブジェクトは、振る舞いに効く区分だけを状態に持つ。金額そのものではなく `overLimit: boolean`、住所ではなく `domestic: boolean`。区分の決め方そのもの（いくらから上限超えか）は `decisions` に書く

### 3. 作る操作（ファクトリ）で、誰が・何を入力すると作れるかを書く

「誰が作れるか」「どんな入力なら作れるか」が業務の決まりなら、`initial` を関数で書く。

```ts
export const inputs = {
  initial: { ニュース: ["news", "速報"], コラム: ["column", "連載"], 題名が空: ["news", ""] },
};

/** 記事を書き始める */
export function initial(user: User, kind: Article["kind"], title: string): Article {
  ensure(user.role === "author", "著者だけ");
  ensure(title.trim() !== "", "題名が必要");
  return { status: "draft", kind, featured: false, authorId: user.id };
}

export const scenarios = {
  書き始めて公開する: [
    { do: initial, by: "著者alice", input: "ニュース" },
    { do: publish, by: "著者alice", expect: { status: "published" } },
  ],
  読者は書き始められない: [{ do: initial, by: "読者carol", input: "ニュース", denied: "著者だけ" }],
};
```

- 作れた結果がそれぞれ初期状態になる。作ったときに決まる値（`kind`）は、入力の例で値ごとに作る（`variants` は使わない）
- 作る人が所有者になる（`authorId: user.id`）とき、作れる登場人物が 2 人いると、所有者ごとに同じ形の初期状態が並ぶ。所有者を区別する条件（「自分の記事だけ」）を確かめたいなら、作れる人を 1 人にし、ほかの登場人物は「作れない人」か「別の著者」として残す
- 作ることに決まりがない（誰でも、いつでも作れる）なら、`initial` はオブジェクトのままでよい

### 4. 操作はコマンドとして、業務の動詞で名付ける

- `publish`（公開する）、`reject`（差し戻す）のように、業務の人がその出来事を指すときに使う言葉にする。JSDoc の 1 行目が仕様書の見出しになる
- `setStatus(s)`・`update(fields)` のように、入力しだいで何にでも変えられる操作を作らない（DDD でいうドメインモデル貧血症）。どの遷移が許されるかが入力に隠れ、状態遷移図からも `ensure` からも読めなくなる。遷移ごとに操作を分ける
- 1 つの操作は 1 つの集約だけを変える。2 つの集約を同時に変える必要があるように見えたら、手順 1 の境界を見直すか、手順 6 のつながりにする

### 5. 事前条件と 2 種類の不変条件を書き分ける

条件の置き場所は、何について述べているかで決める。

| 述べていること | 置き場所 | 例 |
|---|---|---|
| この操作を、いま、この人が、この入力でできるか | `ensure` | `ensure(user.role === "editor", "編集者だけ")` |
| どの状態でも成り立つこと | `invariants` の `(state) => boolean` | 固定できるのは公開中の記事だけ |
| どの遷移でも成り立つこと（ライフサイクル） | `invariants` の `(before, after) => boolean` | 成功か取り消しで終わったジョブは変わらない |
| 「誰が」「入力」についての決まりの意図 | `denied` の手順を持つシナリオ | 理由を書かずには差し戻せない |

```ts
const isFinished = (job: Job) => job.status === "succeeded" || job.status === "cancelled";

export const invariants = {
  成功か取り消しで終わったジョブは変わらない: (before: Job, after: Job) => !isFinished(before) || before.status === after.status,
};
```

遷移の不変条件を 1 つ書くと、状態についての `ensure`（「待機中のときだけ」「実行中のときだけ」）の多くが、その決まりで確かめられるようになる。`examples/job-api.spec.ts` では、意図がほかに書かれていない条件が 10 件から 5 件に減った。残る「誰が」の条件は、不変条件では書けないので `denied` のシナリオで書く。

### 6. ほかの集約とは、ID とつながりで結ぶ

- データとして相手を持つ関係（記事の著者）は、`@ref` を付けた ID の項目で書く。一覧ページの「関連」の図になる
- 「注文を確定したら、在庫を引き当てる」のように、ある操作がほかの集約の操作を起こすなら、起こす側の spec に `links` を書く。相手の操作は相手の spec に書き、相手の条件で止まりうる（結果整合性）ことを前提にする。同じ操作の中で相手の状態まで書き換えない

```ts
export const links = [{ from: confirm, to: "stock", action: "reserve", label: "注文を確定したら在庫を引き当てる" }];
```

### 7. 業務のルールは判断表に切り出す

送料・割引・料金区分のように、状態遷移ではなく「入力の組み合わせ → 結果」で決まるルールは `decisions` に書く。集約の状態には、判断の結果の区分（`overLimit` など）だけを持たせる。

### 8. ユビキタス言語をそろえる

- `glossary`、状態の型の項目の JSDoc、`ensure` の理由、操作の見出しは、業務の人が使う言葉で書く。開発者の言葉（`flag`、`record`、`process`）を持ち込まない
- 同じ条件には同じ理由の文を使う（「編集者だけ」と「エディターのみ」を混ぜない）
- 同じ言葉が spec によって違う意味になっていたら（請求の「確定」と配送の「確定」など）、言葉を分けるか、別のコンテキストとして扱う。意味が決められなければ `questions` にする

### 9. 分からないことは業務の人に聞く

DDD でいう知識の噛み砕きは、推測でモデルを埋めないことから始まる。要件やコードから決められないこと（アーカイブした記事を戻せるか、など）は `questions` に書き、対象の操作か状態を `about` で指す。

## 検査結果から設計の問題を読み取る

| live-spec の検査結果 | DDD での読み方 | 直し方 |
|---|---|---|
| 状態が 10 個を超える・状態の数の上限で打ち切り | 集約が大きすぎる | 手順 1 で不変条件を書き出し、同時に守らなくてよい関心を別の spec に分ける |
| 振る舞いが同じ状態（`equivalent-states`） | 意味のない区別を状態に入れている。または、区別を生む概念が抜けている | 区別が要らないなら項目を外す。要るなら、その違いが効く操作か条件を足す |
| どの可否にも影響しない項目（`unused-field`） | 集約の外に置くべき値（データ、ほかの集約）を状態に入れている | データにするか、`@ref` を付けた参照にする |
| 誰でもできる（`anyone-can`）・本人と別人を区別しない（`same-for-similar-actors`） | 「〜だけ」「自分の〜だけ」の事前条件が抜けている | `ensure` を足し、`denied` のシナリオで意図を書く |
| いつでもできる（`anytime`） | ライフサイクルの条件が抜けている | `ensure` を足すか、遷移の不変条件で決まりを書く |
| 意図がほかに書かれていない条件（`unguarded`）が状態の条件に多い | ライフサイクルの決まりが書かれていない | 手順 5 の遷移の不変条件を書く |
| 不変条件を破る | 集約の境界の中で、操作が不変条件を守り切れていない | 操作の戻り値を直す。境界の外の値で破っているなら、手順 1 の境界を見直す |
| 目指す状態にたどり着けない（`cannot-reach-goal`） | ライフサイクルに袋小路がある | 抜け出す操作を足すか、終端として認める |

## やらないこと

- DDD の用語（集約、エンティティなど）を、仕様書に出る文（JSDoc、`ensure` の理由、`glossary`）に持ち込まない。仕様書の読み手は業務の人なので、DDD の用語は設計のための道具にとどめる
- リポジトリ・アプリケーションサービス・ドメインイベントのクラスなど、実装の構造を spec に書かない。spec は振る舞いの正本で、実装の構造は実装が決める
- 集約を分けるためだけに、業務の人が区別しない概念を作らない。分けた結果の名前が業務の言葉にならないなら、分け方を見直す
