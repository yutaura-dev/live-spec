# 既存のコードから spec を書き起こす

書き起こす spec は「**今のコードがどう振る舞うか（as-is）**」の仕様。あるべき姿ではない。読み手は生成された仕様書を見て「うちのシステムは本当にこう動くのか」を確かめるので、spec の 1 行 1 行がコードのどこに対応するかを追えることが価値になる。

spec の書き方の規約は [live-spec-authoring](../live-spec-authoring/SKILL.md) に従う。先に読むこと。

## 1. 範囲を決め、ドメインオブジェクトに分ける

リポジトリ全体を一度に書き起こさない。依頼された機能に関わる**ドメインオブジェクトを洗い出し、1 つずつ別の spec にする**（注文、決済、配送…／サーバ、ブラウザのタブ、監視のセッション…）。ユーザーが対象を指定していなければ、候補を挙げて選んでもらう。

分け方の目安: 「状態を表す値」と「それを変える操作」が独立しているものは別のオブジェクト。1 つの spec の状態が 10 個を超えそうなら、関心の違うものを混ぜている。例えば「サーバが待ち受け中か」と「ブラウザのタブが最新を表示しているか」は別々に変わるので、別のオブジェクトにする。混ぜると状態が掛け算で増え、図が読めなくなる。

## 2. コードから材料を集める

| 集めるもの | 探す場所 | 例（rg のパターン） |
|---|---|---|
| 状態 | enum・リテラル union、DB の status / state 列、`*_at` の有無で決まる暗黙の状態、`is_*` の真偽値、reducer、状態機械 | `status`, `state`, `enum `, `_at\b`, `createMachine` |
| 操作 | 状態を書き換える場所（ハンドラ、ルート、ミューテーション、コマンド、サービスのメソッド） | `status\s*[:=]`, `update\(`, `router\.(post\|put\|patch\|delete)` |
| 誰が | 認証ミドルウェア、ポリシー、ロール判定、所有者の比較 | `role`, `can\(`, `authorize`, `ownerId\|userId\s*===` |
| いつ | ガード条件、早期 return、例外、バリデーション | `throw`, `return .*(40[0-9])`, `if \(!` |
| 入力 | リクエストのスキーマ、引数のバリデーション | `z\.object`, `body\.`, `parseArgs` |
| 画面 | ボタンの出し分け、API のレスポンス、CLI の出力 | `disabled`, `res\.status`, `console\.(log\|error)` |

集めたら、spec を書く前に「状態の候補・操作の一覧・各操作の条件」をメモにまとめる。この段階で、状態に入れない値（表示用の値、件数など）を決める。

## 3. 根拠を残しながら書く

spec の各操作と ensure に、根拠となるコードの場所を `// 根拠: path:line（補足）` の形のコメントで残す。レビューする人が spec とコードを突き合わせられるようにするため。操作の関数の中に書いた根拠は、仕様書の操作カードにも「根拠」として表示される（絶対パスは書かない。共有したときに手元の環境が漏れるため）。

```ts
/** 注文を確定する */
export function confirm(order: Order, user: User): Order {
  // 根拠: src/orders/routes.ts:88（requireRole("staff")）
  ensure(user.role === "staff", "店舗スタッフだけ");
  // 根拠: src/orders/service.ts:42-45
  ensure(order.status === "pending", "受付待ちのときだけ");
  return { ...order, status: "confirmed" };
}
```

## 4. 推測で埋めない

コードから読み取れたことと、推測したことを分ける。分からないことを「もっともらしく」書くと、仕様書が作り話になり、人がそれを信じてしまう。

- **確認済み**: コードに根拠がある。そのまま書く
- **推測**: 命名やコメントからそう読めるが、コードで確かめられない。書くなら `// 推測: …` と残し、報告に挙げる
- **不明**: 外部サービスの挙動、設定値による分岐、DB の制約だけで決まることなど。spec に書かずに質問にする

コードに不整合がありそうでも、**直さずに今の動きのまま書く**。例えば「画面ではボタンが出るのに API は 403 を返す」なら、両方をそのまま spec にすると live-spec の検査が食い違いとして指摘する。それを報告に挙げ、どちらが正しいかを人に判断してもらう。

## 5. 生成して突き合わせる

1. spec を生成し、検査結果を読む（読み方は live-spec-authoring）
2. 検査結果ごとに「モデルの誤り」か「コードの実際の振る舞い」かを判断する。前者は spec を直す。後者は報告に挙げる
3. 生成された「できる人／できるとき／できないとき」を、もう一度コードと見比べる。表に出ている理由が、コードの条件と同じ意味になっているかを確かめる
4. 型チェックを通す
5. 生成した HTML を開いて、人が読めるかを確かめる。状態遷移図が線で埋まっていたり、状態名が項目の値の羅列になっていたりしたら、ドメインオブジェクトの分け方を見直す

## 6. 保存場所とセットアップ

- spec は 1 つのディレクトリ（例: `specs/`）にまとめ、`live-spec specs/ --html --out <file>` で 1 つの HTML にする
- spec を置く場所（例: `specs/`）と、`npm i -D @yutaura/live-spec`（または pnpm / yarn）で依存を足してよいかを、**書き込む前にユーザーに確認する**。package.json を勝手に変えないため。spec からは `import { ensure, ui, api, cli } from "@yutaura/live-spec"` で読み込む
- **live-spec リポジトリ自身が対象**: `specs/` に置き、`../src/index.ts` から読み込む

## 7. 報告する

次の形で報告する。人が判断すべきことを先に、細部は後に。

```markdown
## 書き起こした仕様: <対象>

- 仕様書: <HTML のパス、または --serve の URL>
- spec: <spec のディレクトリと、ドメインオブジェクトの一覧（名前と一言の説明）>

### 判断してほしいこと
1. <質問。コードのどこを見てそう思ったかを添える>

### 実装の不整合かもしれない点
- <検査結果と、その根拠のコードの場所>

### モデルにしたこと
- 状態: <項目と取りうる値>。状態から外した値: <値と理由>
- 登場人物: <一覧と、その組にした理由>
- 範囲外にしたこと: <操作・画面など>

### 推測で書いたところ
- <spec の場所と、推測の根拠>
```
