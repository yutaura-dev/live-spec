# spec の変更をレビューする

spec の差分（TypeScript の diff）をそのまま読ませても、人には振る舞いの変化が分からない。`ensure` の 1 行の変更が「閲覧者が公開できるようになった」という重大な変化だったりする。この skill では、変更前と変更後の spec をそれぞれ live-spec で**実行**し、結果を比べて「振る舞いの変化」として報告する。

## 差分を取る
`live-spec diff` を使う。変更前と変更後の spec を、どちらも実行して比べる。ディレクトリを渡せば、ドメインオブジェクトごとに「追加・削除・変更・変化なし」を判定する。

```sh
# 作業ツリーの spec と HEAD を比べる
npx live-spec diff specs/

# PR のように、ブランチ同士を比べる（--head を省くと作業ツリー）
npx live-spec diff specs/ --base origin/main --head HEAD

# 人に見せるなら HTML（重ね合わせた状態遷移図と、画面の変更前・変更後が並ぶ）
npx live-spec diff specs/ --base origin/main --html --out spec-diff.html
```

出力には次が含まれる。状態は値で比べる（ID は探索順で振り直され、名前は `initial` の書き順で変わるため）。

- ドメインオブジェクトごとのまとめの表
- 変更前と変更後を重ねた状態遷移図（増えた・消えた・通れる人が変わった遷移）
- 操作・状態・遷移の増減
- できる／できないが入れ替わったもの。できない理由の言い方だけが変わったものは、別にまとめて件数を出す
- シナリオ・未決事項・検査結果の増減（検査結果は、最短の手順だけが変わったものは差分にしない）
- 画面が変わった状態と登場人物

spec が相対パスで import している別ファイル（共通の型など）は、変更前の側でも作業ツリーの版が使われる。そのファイルを変えた PR では、差分を割り引いて読む。

## 読み方

差分の中で、人の判断が特に必要なものを先に挙げる。

1. **権限が広がった変化**: ❌ から ✅ に変わった行。特に「誰が」の理由（「編集者だけ」など）が消えたもの。意図しない権限の拡大はバグになりやすい
2. **消えた状態・遷移**: それまでできた業務ができなくなっていないか
3. **新しい検査結果**: 不変条件の違反、画面と操作の食い違いなど
4. **確かめてほしい点**: 仕様書の上部の一覧（誰でもできる・いつでもできる・本人と別人を区別しない、意図がほかに書かれていない条件、など）。変更で増えたものは、条件の書き忘れの候補として必ず挙げる。`reviewed` に足された理由も、要件として妥当かを確かめる
5. **理由と「通るのは」の食い違い**: 変更した操作の「条件」の各行で、理由の文と「通るのは〜のとき」を読み比べる。食い違う行は、条件か理由の書き間違いとして必ず挙げる
6. **画面の変化**: 状態と見る人を挙げ、HTML で確認してもらう（`npx live-spec <dir> --serve` で開き、`#/<名前>/<状態>` で直接開ける）

spec のコードの差分（`git diff`）は、変化の理由を説明するときの補足として読む。

## 報告の形

```markdown
## spec の変更: <対象>

<変化を 2〜3 文で。業務の言葉で書く。例:「閲覧者も記事を公開できるようになった。差し戻しに理由の入力が必須になった。」>

### 確認してほしいこと
1. <権限の拡大や、消えた業務など、意図を確かめたい変化>

### 振る舞いの変化
<live-spec diff の出力を、意味のまとまりごとに整理したもの。表はそのまま貼ってよい>

### 新しい検査結果
- <あれば。なければ「なし」>
```

「変化なし」だった場合も、そう報告する。リファクタリングで振る舞いが変わっていないことの確認になる。

## 実装より先にレビューする

spec が正本で、実装は spec に従う（live-spec-authoring の「spec が先、実装が後」）。振る舞いを変えるときは、spec の変更を実装の前にこの skill でレビューし、人が承認してから実装に入る。実装と spec を同じ PR に入れるときも、spec の変更を先に見せて合意を取る。

## 実装と spec のずれを見つけたとき

ずれを見つけても、spec を実装に合わせて書き換えない。

1. `live-spec check specs/ --tests <テストのディレクトリ>` を実行する。spec に無い項目を指すテストは、spec の変更に実装とテストが追いついていない印。テストのない条件（`untested:…`）は、実装が守っているかを確かめていない条件
2. 実装の差分に、spec に無い振る舞いの変更（権限が変わった、状態が増えた など）があれば、報告に挙げる。spec の変更として出し直してレビューするか、実装を戻すかは人が決める
3. spec のほうが誤っていたと分かったときも、その場で書き換えず、spec の変更として差分を出してレビューを受ける
