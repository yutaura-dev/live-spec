# Charter: live-spec

このプロジェクトのアイデンティティを定める文書。**変更するときは ADR が必須**。

## 存在意義 (Why)

**AI が書いた仕様を、人が見て理解して承認できるようにする。**

OpenSpec、GitHub Spec Kit、Kiro、BMAD などの spec-driven development ツールでは、仕様の実体が大量の markdown です。AI が読むには問題ありませんが、人がレビューするには負担が大きすぎます。Scott Logic の検証では、コード 689 行に対して markdown が 2,577 行生成されました。結果として、人は読まずに承認するか、仕様を読まなくなるかのどちらかになります。

live-spec は、次の 3 つを満たす「生きた仕様書」を作って管理します。

1. **実行可能**: 仕様から導いたテストが通ることで、仕様が正しいと示せる
2. **状態遷移を図で見られる**: 振る舞いの全体像を文章ではなく図で把握できる
3. **ワイヤーフレーム（サーフェス）がある**: 各状態で外から何が見えるかが具体的に分かる

## 想定ユーザー (Who)

- **当面**: メンテナ本人。Claude Code などの AI エージェントに仕様を書かせ、それを自分がレビューする
- **将来**: 出来がよければ OSS として公開し、同じように AI と協働する開発者に使ってもらう

### 既存の代替手段との違い

- **SDD ツール（OpenSpec、Spec Kit、Kiro）**: 仕様が markdown なので、人が読む負担が大きい。live-spec では markdown は表示形式の 1 つにすぎない
- **Stately Studio / XState**: 状態遷移の可視化とテスト生成は強いが、画面などのサーフェスと結びついていない
- **Sketch.systems**: 状態と画面のプロトタイプが結びついていて構想に一番近いが、検証機能がなく、開発もほぼ止まっている
- **Concordion / Cucumber**: 実行可能な仕様だが、状態遷移の全体像が見えない

調査の詳細は [research/2026-11-prior-art.md](research/2026-11-prior-art.md) にあります。

## やること (In Scope)

- **AI が書く構造化された仕様フォーマット**: 状態・遷移・サーフェス・シナリオ・未決事項を表す
- **人向けのビューア**: 状態遷移図とサーフェスを組み合わせた wireflow 表示。概要から詳細へ段階的に見せる
- **実行**: 仕様からテストの経路を生成して実行し、結果を図の上に重ねる
- **網羅性の lint**: 到達できない状態、行き止まりの状態、サーフェスやテストが割り当てられていない遷移を見つける
- **図の差分レビュー**: 仕様の変更を、状態や遷移の追加・削除として図の上で見せる

対象は **Web UI に限りません**。API、CLI、データ基盤の振る舞いも状態機械とサーフェスで表します。

## やらないこと (Out of Scope) ⚠ 重要

- **本格的なデザインツールにはしない**。サーフェスはわざと低忠実度にとどめる。見た目の議論ではなく、振る舞いの議論に集中させるため
- **テストランナーは自作しない**。Vitest や Playwright などの既存ランナーの上に載せる
- **SaaS 化・ホスティング・リアルタイム共同編集はしない**。ローカルと git で完結させる
- **仕様を書く AI エージェント本体は作らない**。Claude Code などの既存エージェントに「使われる側」として、フォーマット、CLI、MCP などを提供する
- **仕様の正本を markdown にしない**。markdown は生成される表示形式の 1 つにとどめる

## 隣接プロジェクトとの境界

- **XState / Stately**: 置き換えずに連携する。import と export の対象にする
- **Storybook / Playwright / Vitest**: サーフェスとテストの実行先として使う
- **Mermaid**: GitHub 上で見るための出力形式として使う

## 成功条件 (Success Criteria)

- 自分のプロジェクトの少なくとも 1 つで、仕様を live-spec で管理している
- AI が出した仕様変更を、**正本のテキストや markdown を開かずに**、図・サーフェス・差分のビューだけでレビューして承認できる
- 「人が読まずに承認する」ことがなくなったと自分で感じられる

## 撤退条件 (Sunset Criteria) ⚠ 重要

> 暫定（AI の提案）。初回の見直しは Phase 1 の完了時に行う。

- **3 か月続けて、自分のどのプロジェクトでも使わなかったら凍結する**
- **レビューのたびに正本のテキストを直接読む必要が出て、それが常態化したら、方針を見直す**。存在意義そのものが満たせていないため
- **既存ツールが「状態遷移、サーフェス、実行、差分」を統合したら、そちらに移る**。たとえば Stately がサーフェスとの紐付けを実装した場合
- **メンテナンスにかかる時間が、レビューで減らせた時間を上回ったら、縮小か凍結を検討する**

## 後継への移行パス

正本は構造化データなので、XState や Mermaid などへの export を経路として持つ。撤退するときは、各プロジェクトの仕様をそれらの形式に書き出して手放す。

## 前提と制約

- 仕様を書くのは AI エージェントであることを前提にする。人が手で書きやすいかどうかは二の次
- 個人開発なので、メンテナンスのコストを小さく保つことを最優先にする
