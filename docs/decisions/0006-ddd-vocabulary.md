# ADR-0006: spec の概念を DDD の語彙で定義し、集約のライフサイクルを書けるようにする

- **Status**: Proposed
- **Date**: 2026-11-28
- **Deciders**: YutaUra

## Context

live-spec の spec は、操作を `(状態, 登場人物, ...入力) => 次の状態` の純粋関数で書き、できない理由を `ensure` で書く（[ADR-0005](0005-domain-object-centric-model.md)）。この形は、Eric Evans の Domain-Driven Design（DDD）の「集約へのコマンド」と「事前条件（アサーション）」にほぼ一致する。しかし、live-spec の用語は DDD の用語と結びつけて定義されていなかった。そのため次の問題があった。

- 「ドメインオブジェクト」が何を指すのかがぶれる。DDD ではエンティティと値オブジェクトの総称なので、1 ファイルに何を入れるかの判断材料にならない
- spec を書く AI が、DDD の設計の知識（集約の境界は不変条件で決める、ほかの集約は ID で参照する、など）を使えない
- 集約のライフサイクルの決まりのうち、2 つが書けなかった
  - **作ること**: 初期状態は `initial` のオブジェクトで与えるだけで、「誰が作れるか」「どんな入力なら作れるか」を書けない（DDD のファクトリに当たる）
  - **遷移の前後の決まり**: 「終わったジョブは変わらない」のような、遷移の前と後を比べる不変条件を書けない（plan.md で未着手だった項目）

## Decision

### 1. 用語を DDD の語彙に対応づける

| live-spec | DDD |
|---|---|
| ドメインオブジェクト（spec ファイル 1 つ） | **集約**。集約ルートのエンティティ 1 つのライフサイクルを書く。一緒に守る必要がある不変条件の範囲が 1 つの集約になる |
| 状態の型 | 集約ルートのエンティティ |
| 状態の中のオブジェクト・判別 union | 値オブジェクト |
| `@ref` の項目・型がほかの spec の状態の型になっている項目 | ほかの集約への参照（ID で参照する） |
| 操作 | 集約へのコマンド。業務の動詞で名付ける |
| `ensure` | コマンドの事前条件 |
| `invariants` | 集約の不変条件 |
| `initial` の関数 | ファクトリ（作る操作） |
| `links` | 集約をまたぐ反応（ポリシー）。ほかの集約とは結果整合性で足りる |
| `decisions` | ポリシー・仕様パターン |
| `glossary`・JSDoc・ensure の理由 | ユビキタス言語 |
| プロジェクト（spec のディレクトリ） | 境界づけられたコンテキスト（今は 1 つとして扱う） |

利用者向けの言葉は「ドメインオブジェクト」のままにし、定義で「DDD の集約に当たる」と書く。そうすれば、DDD を知らない人にもとっつきやすく、知っている人には定義で通じる。

### 2. 引数を 2 つとる不変条件を、遷移の不変条件とする

`invariants` のうち `(before, after) => boolean` と書いたものは、探索で見つけたすべての遷移について、遷移の前と後の状態で確かめる。不変条件を破った遷移は、その遷移までの最短手順と一緒に検査結果に出す。`ensure` のミューテーションでも「気づくもの」に数える。

### 3. `initial` を関数でも書けるようにし、作る操作とする

`export function initial(登場人物, ...入力): 状態` と書くと、作る操作になる。登場人物と、`inputs.initial` に書いた入力の例とのすべての組で実行し、作れた結果をそれぞれ初期状態にする。`ensure` で止まった組は「作れない理由」として仕様書に出す。シナリオは最初の手順に `{ do: initial, by, input }` を書いて始められ、`denied` で「作れないはず」も書ける。

作る操作があるときは、作ったときに決まる値ごとの初期状態や `variants` は使わない。どんな初期状態がありうるかは、作る操作とその入力の例から決まるからである。

## Alternatives Considered

- **用語そのものを「集約」に変える**: DDD を知らない読み手にとって「集約」は意味が取りにくい。仕様書の読み手にはコードを読まない人も含まれるので、見出しの言葉は変えず、定義で結びつける
- **遷移の不変条件を別の export（`transitions` など）にする**: 1 つの状態についての条件と遷移の前後についての条件は、どちらも「いつも成り立つべきこと」なので、置き場所を分けると書き手が迷う。引数の数で見分ける
- **作る操作を別の名前（`create`）の export にする**: `initial` と `create` の両方があるときの規則が要る。`initial` を「初期状態の作り方」として、オブジェクトでも関数でも書けるようにするほうが覚えることが少ない
- **作る操作が返すイベントを書けるようにする（Decider パターン）**: 操作が状態ではなくイベントを返す形にすると、spec が倍の長さになり、AI が評価前のコードを読んで構造をつかみにくくなる。集約をまたぐつながりは `links` で書き、イベントに名前を付けることは次の段階で考える

## Consequences

### Positive

- spec を書く AI に、DDD の知識をそのまま使ってよいと伝えられる（skill の live-spec-domain-modeling）
- 「誰が作れるか」「どんな入力なら作れるか」が、操作と同じ形で仕様書に出る
- 状態についての `ensure` の意図を、ライフサイクルの決まり 1 行で書ける。`examples/job-api.spec.ts` では、意図がほかに書かれていない条件が 10 件から 5 件に減った

### Negative

- 作った人によって所有者が決まる spec（`authorId: user.id`）では、作れる登場人物の数だけ初期状態が増える。所有者ごとに同じ形の状態遷移図が並ぶので、作れる人を 1 人にするか、初期状態をオブジェクトで書く
- 作る操作の `ensure` は、まだミューテーション（条件の効き目）と「確かめてほしい点」の対象にしていない
- 遷移の不変条件は、操作の名前や登場人物を受け取らない。「管理者が取り消したときだけ〜」のような決まりは書けない

### Neutral

- 境界づけられたコンテキスト（プロジェクトを複数のコンテキストに分けること）とドメインイベントの名前は、この ADR では扱わない
