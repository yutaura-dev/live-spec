# ADR-0007: 値オブジェクトを別のファイル（*.value.ts）で定義する

- **Status**: Accepted
- **Date**: 2026-11-28
- **Deciders**: YutaUra

## Context

[ADR-0006](0006-ddd-vocabulary.md) で、spec ファイル 1 つを DDD の集約（ルートのエンティティ）に、状態の中のオブジェクトや判別 union を値オブジェクトに対応づけた。値オブジェクトは、状態の型の項目として書き、プロパティの表で子の行として展開して見せている。この形には 2 つの不足があった。

- 同じ値オブジェクト（作業する場所など）を複数の spec が持つと、定義が spec ごとのページに重複して出る。定義の正本がどこかが読めない
- 値オブジェクト自身の決まり（「金額は 0 以上」「URL は http か https で始まる」）を書く場所がない。DDD では、値オブジェクトを作る時点で確かめる不変条件に当たる

## Decision

### 1. 値オブジェクトは `<名前>.value.ts` に書く

spec と同じディレクトリに置く。次を export する。

- 型: ファイル名から作った名前の型（`place.value.ts` なら `Place`）。なければ最初に export した型
- `invariants`: 正しい値の決まり。`{ 説明: (値) => boolean }`
- `examples`: `{ valid: { 例の名前: 値 }, invalid: { 例の名前: 値 } }`

live-spec は、正しい例がすべての決まりを満たし、正しくない例がどれかの決まりを破ることを確かめ、そうでなければ検査結果に出す（`check` を失敗させる）。

### 2. 値オブジェクトは専用のページにせず、一覧ページの節に出す

値オブジェクトには識別子もライフサイクルもない（変えるときは別の値に取り替える）ので、状態遷移図・操作・シナリオを持たない。一覧ページの「値オブジェクト」の節に、項目の表・正しい値の決まり・例の結果を並べる。spec が 1 つでも値オブジェクトがあれば、一覧ページを出す。ドメインオブジェクトのプロパティの表では、型が値オブジェクトの型の項目の扱いを「値オブジェクト（名前）」とし、その節へリンクする。

### 3. 画面の呼び名は「ドメインオブジェクト」のままにする

spec ファイル 1 つは、ADR-0006 のとおり画面では「ドメインオブジェクト」と呼ぶ。値オブジェクトと対にして説明するときだけ、DDD の言葉（集約のルートのエンティティ）で定義する。

## Alternatives Considered

- **spec ファイルを「エンティティ」と呼び直す**: spec 1 つは、ルートのエンティティとその中の値オブジェクトを含む集約なので、「エンティティ」と呼ぶと範囲がずれる。また、仕様書の読み手には DDD を知らない人も多い（ADR-0006 で「集約」を見送ったのと同じ理由）
- **値オブジェクトにもエンティティと同じページを作る**: 状態遷移図と操作がない値オブジェクトでは、ページの大半が空になる。項目・決まり・例は、一覧ページの節で足りる
- **値オブジェクトの決まりを spec の `invariants` に書く**: spec の不変条件は状態（集約）についての決まりで、値オブジェクトが集約の外でも同じ決まりを持つことを表せない。複数の spec が同じ値オブジェクトを持つと、決まりが spec ごとに重複する

## Consequences

### Positive

- 値オブジェクトの定義と決まりが 1 か所にまとまり、例で確かめられる
- 値オブジェクトの型を spec から import して使えるので、型と決まりが同じ正本になる

### Negative

- 値オブジェクトの決まりは例でしか確かめないので、spec の探索の中で作られた値が決まりを満たすかは確かめていない

### Neutral

- 値オブジェクトのファイルの変更は、`--watch` で spec と同じように生成し直す
