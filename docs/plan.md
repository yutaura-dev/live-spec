## MVP 定義

**AI に仕様を書かせ、人が図とサーフェスを見て理解できる。** 実行と差分は MVP に含めない。

完了条件:
- [ ] AI（Claude Code）が、フォーマットの説明だけを手がかりに正本を書ける
- [ ] 正本から、状態遷移図とサーフェスを組み合わせた wireflow ビューを生成できる
- [ ] 網羅性の lint が、到達できない状態、行き止まりの状態、サーフェスが割り当てられていない状態を検出できる
- [ ] UI・API・CLI のうち少なくとも 2 種類の題材で、仕様を表現できる

## フェーズ計画

### Phase 0: フォーマット設計の spike

**目標**: 正本のフォーマット（YAML か TS DSL か、など）と技術スタックを決める

**完了条件 (Definition of Done)**:
- [x] UI の題材（例: ログインフロー）と API または CLI の題材の 2 つで、フォーマット案を 2 案以上書いて比べた（[spikes/phase0/](../spikes/phase0/comparison.md)）
- [x] フォーマットと技術スタックの決定を ADR に記録した

**想定タイムライン**: TBD（次回更新時に決める）

### Phase 1: MVP（書かせて、見られる）

**目標**: 正本、ビューア、lint の 3 つがそろい、自分のプロジェクトで使い始められる

**完了条件**:
- [ ] 上の MVP 完了条件をすべて満たす
- [ ] 自分のプロジェクト 1 つで、実際に仕様を管理し始めた

### Phase 2: 実行と差分（確かめて、比べられる）

**目標**: 生きた仕様書の 3 要件をすべて満たす

**完了条件**:
- [ ] 仕様からテストの経路を生成し、既存のテストランナーで実行できる
- [ ] テスト結果とカバレッジ（未検証の遷移）を図の上に重ねて表示できる
- [ ] git の 2 つのリビジョン間の仕様の差分を、色分けした図で見られる

### Phase 3: 乖離の検出と公開

**目標**: 仕様が「生き続ける」仕組みを作り、OSS として公開するか判断する

**候補**:
- 実装のイベントログやトレースが、仕様上ありうる振る舞いかを検査する（PObserve や TLA+ の trace validation に近い方式）
- 既存のコードや XState の定義から、正本を逆生成する
- AI 向けのインターフェース（JSON を返す CLI、MCP）
- OSS として公開するかの判断とライセンスの決定
